# ACP access in OAuth

For the verified OpenAI/Responses compatibility boundary, native CLI capability probes, and proposed session/tool architecture, see [ACP OpenAI compatibility review](acp-openai-compatibility.md).

OAuth contains an ACP Access tab beside sign-in and authentication files. The new tab is independent of the sidebar and existing OAuth credential lists.

The page uses the full available width, with account identity and controls side by side in wide windows. Model verification and API access occupy separate compact panels below; expanding one does not stretch the other. CLI status lives in the account card footer. The Google account → Antigravity CLI → CPA API connection flow, runtime paths, and reauthentication stay in collapsible connection details. Before connecting, model and API panels explain their prerequisites. Adding an account expands a labeled sign-in form; reauthentication explains that it logs out the selected account first. The test model selection does not restrict API models: enabling access exposes all models advertised by the active account. Saved API enablement with a disconnected account is shown as waiting for connection, and can still be disabled.

## Available operations

Account selectors prefer the email reported by the official CLI and append any user label. ACP 1.0 does not expose account identity directly: after a successful connection, ECPA reads only the owned CLI process's recent `server_oauth.go` login-result line from that account profile, without reading credential storage. Only the email is saved as optional private account metadata. A missing or changed log format falls back to the account label. Reauthorization clears the previous identity before starting; privacy mode masks both emails and labels at display time.

- Detect the installed official Antigravity CLI through existing agent discovery.
- Authenticate using its official personal Google OAuth flow.
- Add labeled accounts and switch saved logins. All accounts share one installed CLI executable; only runtime data and model selection are stored separately. The existing default login stays in its original directory.
- Reauthenticate the selected account using official ACP logout, then Google authorization. ECPA does not copy, delete or exchange credential files.
- Check an existing login by creating an ACP session and reading account models.
- Save a selected model and explicitly apply it with session/set_model before testing.
- Send a fixed, real text probe and report the completed response, elapsed time, and first text latency.
- Cancel login, refresh, or test operations. Switching tabs preserves the native operation; app exit signals cancellation.
- Keep the latest successful probe in native memory so switching tabs during or after a test restores its result, including the tested model. Starting another operation or changing the model clears the previous result.
- Bound each ACP request: 30 seconds for initialization/session/model configuration, 5 minutes for browser authentication, and 2 minutes for a text probe. Progress events do not extend the deadline. Timeout and cancellation terminate the owned CLI process before releasing the operation slot.

Runtime data is under core_base_dir()/acp/antigravity. The default account uses this directory; additional accounts use accounts/<generated-id>. These are data directories, not separate CLI installations. accounts.json stores labels and the active account. ECPA does not copy normal Antigravity settings, CPA connection files, or OAuth credentials. The official CLI manages credentials. Each operation launches the same executable directly without a shell. Model endpoint and credential environment overrides are removed to avoid routing back into CPA. The ECPA network proxy is applied to the child process.

The ACP client advertises no filesystem or terminal capabilities. It rejects built-in tool permissions and permits only client-declared MCP function tools. This is a connection/test interface, not a general Agent execution environment or OS sandbox.

## Model list and API access

API access is **off by default**, including for existing login profiles without an explicit saved enablement. Signing in, refreshing, reconnecting, or switching accounts does not enable it. Use the explicit API toggle in the ACP tab after connecting an account. ECPA binds an authenticated loopback listener and registers its reserved ecpa-antigravity-acp OpenAI-compatible provider, preserving other entries. Account models appear as acp/<official-model-id> in CPA /v1/models and ECPA model lists. Use the existing CPA endpoint and client API key for POST /v1/chat/completions. Legacy and v8 configuration layouts are supported.

API intent is stored once in core_base_dir()/acp/antigravity/bridge.json, not in individual accounts/<id> directories. Explicit enablement survives restart and is restored only after verifying the active account. If verification fails, the UI shows enabled access waiting for connection; the disable toggle remains available. Startup rechecks saved intent before registering, so a newer disable wins over an in-progress restore.

Disabling first atomically saves enabled=false, cancels pending tool sessions and the listener/runtime, and removes the managed provider without changing unrelated routes. It is safe to repeat, including without a runtime, provider entry, or kernel configuration. A settings-write failure leaves the previous settings, provider and runtime unchanged and reports an error. A provider-cleanup failure instead fails closed: saved intent stays off and the runtime is cancelled, so a stale provider cannot serve requests or restore access on restart. The cleanup error is shown rather than reporting success; repair the configuration error and retry cleanup. Settings and provider writes use atomic replacement to avoid partially written files.

The bridge accepts text Chat Completions requests, regular responses and SSE. CPA provides the public Responses endpoint by converting requests and responses through its existing OpenAI translator; ECPA does not implement a separate Responses translator. System and developer instructions are delivered separately through the CLI's advertised standard systemPrompt append capability or the official Antigravity _meta.antigravity.systemPrompt.append extension. A CLI without either capability returns an explicit update-required error when instructions are present. Append preserves the Agent's own default instructions; it is not an override. User and assistant history remains flattened as User: <text> and Assistant: <text>, separated by a blank line. A single user turn is sent unchanged. New turns use a fresh CLI session. A tool call retains that live ACP prompt while the API client executes the function; the following tool result continues the same execution. Completed older history is included as text when starting another turn.

Function tools are exposed through an internal authenticated loopback/stdio MCP adapter launched from the same ECPA executable. No user MCP installation or configuration is needed. Chat Completions tool_calls and tool results are supported, including SSE. CPA translates Responses function_call and function_call_output through this same path. Pending calls retain the official CLI process, validate model/account/tool identity and semantic history, and expire after ten minutes. Completed tool IDs cannot be delivered twice. Switching accounts, disabling API access and app shutdown clear pending calls. Empty/null tools, auto, and explicitly disabled tools (none) are accepted. Required/named choices and strict tool schemas are not implemented. Optional n: 1, store: false, response_format type text, parallel_tool_calls booleans, user, metadata, prompt_cache_key and safety_identifier are accepted; identifiers and metadata do not add storage or caching guarantees. Valid max_tokens, max_completion_tokens, temperature and top_p values (including null) are accepted for client compatibility. The official ACP CLI does not expose these controls: its defaults apply, with unapplied non-null parameters listed in the bridge response header x-ecpa-ignored-parameters and a parameter-name-only diagnostic. No precise token limit or sampling setting is enforced. CPA may filter upstream headers; consult the ECPA diagnostic when the header is absent from the public response. Invalid values still return 400. Images and structured output remain unsupported. Function tool loops have been exercised through both protocols, but this is not a claim of complete Codex compatibility: images, strict schemas, required/named choices, Responses compact and every Codex transport require separate implementation or verification.

Thinking levels are detected from official model ID suffixes (none, minimal, low, medium, high, xhigh, max and auto), not display names. reasoning_effort, reasoning.effort and thinking.effort select an advertised family variant through session/set_model. Unknown, unavailable or conflicting levels return errors. Provider thinking levels are not registered automatically. Responses retain the requested model alias. service_tier is rejected because no mapping is implemented. stream_options.include_usage is accepted for CPA compatibility; usage is not fabricated. Request bodies and response text are limited to 1 MiB; system instructions and flattened history share the prompt limit.

One HTTP/native operation runs at a time; concurrent requests return 429. Tool waits release that operation slot while preserving their own CLI execution; at most sixteen pending call IDs are retained. A dropped HTTP/SSE client cancels the operation. Account switching reserves the same slot, clears old capabilities, verifies the selected login and updates models. Saved API enablement restores after app startup by verifying the active account. ECPA must remain running while clients use ACP. Model selection and labels are persisted privately; test results and connection capabilities stay in memory.

## Chat Completions and streaming contract

The public Chat Completions and Responses endpoints continue to use CPA's existing authentication, routing, and protocol translators. The internal ACP listener implements only the OpenAI-compatible upstream contract; it does not add a second public Responses implementation. CPA's Chat-to-Chat response translator passes completion JSON through, so the internal listener must produce complete Chat Completions frames itself.

Successful streams begin with an assistant role delta, followed by text or indexed function tool calls, a single terminal finish reason (`stop` or `tool_calls`), and `[DONE]`. All chunks retain the same completion ID, model, and creation time. Bounded output queues apply backpressure and remain cancellable instead of dropping chunks during a burst. Token usage is omitted when the official CLI does not provide API token counts; `stream_options.include_usage` does not cause fabricated usage.

The listener waits for the first upstream event before committing HTTP 200. Failures before output return an HTTP error through CPA's existing error handling. Failures after output emit a terminal SSE error without a success finish reason or `[DONE]`. This preserves the distinction between an upstream failure and a completed assistant turn. An official CLI quota failure or retry message remains an upstream execution issue; protocol framing cannot restore exhausted model quota.

The isolated CPA contract test checks text replies and tool call/result round trips through both public protocols, including all combinations of streaming and non-streaming tool delivery and continuation. It also checks startup and mid-stream upstream failures. The official ACP process is simulated in this test; no model quota is consumed.

## Verification

- bun run check and bun run build.
- cargo test --manifest-path src-tauri/Cargo.toml acp::tests -- --nocapture.
- cargo test --manifest-path src-tauri/Cargo.toml acp:: -- --nocapture covers account isolation, both provider config schemas, invalid inputs, HTTP replies/SSE, concurrency and disconnect cancellation with a simulated official server.
- Set ECPA_ACP_TEST_CORE to a CPA v8 executable and run cargo test --manifest-path src-tauri/Cargo.toml acp::bridge::tests::real_cpa_lists_and_routes_registered_acp_models -- --ignored --nocapture for isolated CPA model discovery, regular/SSE forwarding and hot-reload removal without a real model call.
- cargo test --manifest-path src-tauri/Cargo.toml acp::rpc::tests -- --nocapture covers silent and continuously updating processes, timeout cleanup, and cancellation before/during a request using isolated test child processes.
- node tests/acp-access-ui.cjs with Playwright available through PLAYWRIGHT_MODULE or node_modules. Covers Chinese/English, model selection, test results, tab remount, keyboard navigation, and narrow layout using synthetic mock data.
- Opt-in real native probe: set ECPA_ACP_PROBE_PROFILE to an officially authenticated isolated profile and ECPA_ACP_PROBE_CLI to the official executable. Run cargo test --manifest-path src-tauri/Cargo.toml acp::tests::official_acp_native_probe -- --ignored --nocapture. The test selects a non-default advertised model and verifies a completed ACP_OK response; it does not print credentials.

Windows verification on 2026-11-16 used official Antigravity CLI 1.4.12. The Rust client successfully selected gemini-4-argon-high and received ACP_OK. macOS and Linux have not been exercised with native CLI installations.
