# ACP access in OAuth

For the verified OpenAI/Responses compatibility boundary, native CLI capability probes, and proposed session/tool architecture, see [ACP OpenAI compatibility review](acp-openai-compatibility.md).

OAuth contains an ACP Access tab beside sign-in and authentication files. The new tab is independent of the sidebar and existing OAuth credential lists.

The page uses the full available width, with account identity and controls side by side in wide windows. Model verification and API access occupy separate compact panels below; expanding one does not stretch the other. CLI status lives in the account card footer. The Google account → Antigravity CLI → CPA API connection flow, runtime paths, and reauthentication stay in collapsible connection details. Before connecting, model and API panels explain their prerequisites. Adding an account expands a labeled sign-in form; reauthentication explains that it logs out the selected account first. The test model selection does not restrict API models: enabling access exposes all models advertised by the active account. Saved API enablement with a disconnected account is shown as waiting for connection, and can still be disabled.

## Available operations

Account selectors prefer the email reported by the official CLI and append any user label. ACP 1.0 does not expose account identity directly: after a successful connection, ECPA reads only the owned CLI process's recent `server_oauth.go` login-result line from that account profile, without reading credential storage. Only the email is saved as optional private account metadata. A missing or changed log format falls back to the account label. Reauthorization clears the previous identity before starting; privacy mode masks both emails and labels at display time.

- Detect the installed official Antigravity CLI through existing agent discovery.
- Authenticate using its official personal Google OAuth flow.
- Add labeled accounts and switch saved logins. All accounts share one installed CLI executable; only runtime data and model selection are stored separately. The existing default login stays in its original directory.
- Reauthenticate the selected account using official ACP logout, then Google authorization. ECPA does not copy, delete or exchange credential files.
- Check an existing login by creating an ACP session and reading account models.
- Save a selected model and explicitly apply it with session/set_model before testing.
- Send a fixed, real text probe and report the completed response, elapsed time, and first text latency.
- Cancel login, refresh, or test operations. Switching tabs preserves the native operation; app exit signals cancellation.
- Keep the latest successful probe in native memory so switching tabs during or after a test restores its result, including the tested model. Starting another operation or changing the model clears the previous result.
- Bound each ACP request: 30 seconds for initialization/session/model configuration, 5 minutes for browser authentication, and 2 minutes for a text probe. Progress events do not extend the deadline. Timeout and cancellation terminate the owned CLI process before releasing the operation slot.

Runtime data is under core_base_dir()/acp/antigravity. The default account uses this directory; additional accounts use accounts/<generated-id>. These are data directories, not separate CLI installations. accounts.json stores labels and the active account. ECPA does not copy normal Antigravity settings, CPA connection files, or OAuth credentials. The official CLI manages credentials. Each operation launches the same executable directly without a shell. Model endpoint and credential environment overrides are removed to avoid routing back into CPA. The ECPA network proxy is applied to the child process.

The ACP client advertises no filesystem or terminal capabilities. It rejects built-in tool permissions and permits only client-declared MCP function tools. This is a connection/test interface, not a general Agent execution environment or OS sandbox.

## Model list and API access

API access is **off by default**, including for existing login profiles without an explicit saved enablement. Signing in, refreshing, reconnecting, or switching accounts does not enable it. Use the explicit API toggle in the ACP tab after connecting an account. ECPA binds an authenticated loopback listener and registers its reserved ecpa-antigravity-acp OpenAI-compatible provider, preserving other entries. Account models appear as acp/<official-model-id> in CPA /v1/models and ECPA model lists. Use the existing CPA endpoint and client API key for POST /v1/chat/completions. Legacy and v8 configuration layouts are supported.

API intent is stored once in core_base_dir()/acp/antigravity/bridge.json, not in individual accounts/<id> directories. Explicit enablement survives restart and is restored only after verifying the active account. If verification fails, the UI shows enabled access waiting for connection; the disable toggle remains available. Startup rechecks saved intent before registering, so a newer disable wins over an in-progress restore.

Disabling first atomically saves enabled=false, cancels pending tool sessions and the listener/runtime, and removes the managed provider without changing unrelated routes. It is safe to repeat, including without a runtime, provider entry, or kernel configuration. A settings-write failure leaves the previous settings, provider and runtime unchanged and reports an error. A provider-cleanup failure instead fails closed: saved intent stays off and the runtime is cancelled, so a stale provider cannot serve requests or restore access on restart. The cleanup error is shown rather than reporting success; repair the configuration error and retry cleanup. Settings and provider writes use atomic replacement to avoid partially written files.

By default CPA sends Chat Completions to the authenticated ACP bridge for both public protocols. CPA converts public Responses requests to Chat Completions and translates the reply back. An [optional native executor](../plugins/acp-responses/README.md) serves public HTTP Responses without that translation; it is source-built, not bundled or enabled automatically. System and developer instructions are delivered separately through the CLI's advertised standard systemPrompt append capability or the official Antigravity _meta.antigravity.systemPrompt.append extension. A CLI without either capability returns an explicit update-required error when instructions are present. Append preserves the Agent's own default instructions; it is not an override. User and assistant history remains flattened as User: <text> and Assistant: <text>, separated by a blank line. A single user turn is sent unchanged. Ordinary Chat turns use a fresh CLI session. A tool call retains that live ACP prompt while the API client executes the function; the following tool result continues the same execution. Completed older history is included as text when starting another turn.

Function tools are exposed through an internal authenticated loopback/stdio MCP adapter launched from the same ECPA executable. No user MCP installation or configuration is needed. Chat Completions tool_calls and tool results are supported, including SSE. The default CPA route translates Responses function_call and function_call_output through this same path; the optional native executor preserves them as Responses items. Pending calls retain the official CLI process, validate model/account/tool identity and semantic history, and expire after ten minutes. Completed tool IDs cannot be delivered twice. Switching accounts, disabling API access and app shutdown clear pending calls. Empty/null tools, auto, and explicitly disabled tools (none) are accepted. Required/named choices and strict tool schemas are not implemented. Optional n: 1, store: false, response_format type text, parallel_tool_calls booleans, user, metadata, prompt_cache_key and safety_identifier are accepted; identifiers and metadata do not add storage or caching guarantees. Valid max_tokens, max_completion_tokens, temperature and top_p values (including null) are accepted for client compatibility. The official ACP CLI does not expose these controls: its defaults apply, with unapplied non-null parameters listed in the bridge response header x-ecpa-ignored-parameters and a parameter-name-only diagnostic. No precise token limit or sampling setting is enforced. CPA may filter upstream headers; consult the ECPA diagnostic when the header is absent from the public response. Invalid values still return 400. Inline images require the connected CLI to advertise image input. Structured output remains unsupported. Function tool loops have been exercised through both protocols, but this is not a claim of complete Codex compatibility: images, strict schemas, required/named choices, Responses compact and every Codex transport require separate implementation or verification.

Thinking levels are detected from official model ID suffixes (none, minimal, low, medium, high, xhigh, max and auto), not display names. reasoning_effort, reasoning.effort and thinking.effort select an advertised family variant through session/set_model. Unknown, unavailable or conflicting levels return errors. Provider thinking levels are not registered automatically. Responses retain the requested model alias. service_tier is rejected because no mapping is implemented. stream_options.include_usage is accepted for CPA compatibility; usage is not fabricated. Request bodies and response text are limited to 1 MiB; system instructions and flattened history share the prompt limit.

By default, one HTTP/native operation runs at a time and concurrent requests return 429. Tool waits release the HTTP slot while preserving their own CLI execution. At most 16 live or waiting ACP sessions are retained across accounts. A dropped HTTP/SSE client cancels in-flight work. Switching accounts, signing out, or disabling API access retires suspended sessions; account management remains exclusive with active HTTP work. Cancel in-flight work before retrying an account action that reports busy. ECPA must remain running while clients use ACP.

### Multi-account concurrency pool, routing & failover

Multi-account concurrency pooling is controlled directly from the **ACP Access** page (and persisted in `core_base_dir()/acp/antigravity/bridge.json`, keeping `enabled` and `port` backwards-compatible with [`plugins/acp-responses`](../plugins/acp-responses/README.md)):

- **Pool toggle (`account_pool`, default `false`)**: When disabled, API traffic routes strictly to the active account (up to its configured `max_concurrency`). When enabled, API traffic distributes across all enabled, saved pool accounts (the default CLI account when saved, plus all separately authorized isolated accounts whose private token file passes read-only verification). Legacy non-isolated secondary accounts are never pooled.
- **Routing strategies (`routing_strategy`, default `round_robin`)**:
  - `round_robin`: Fairly rotates across eligible accounts within the highest available priority tier (`priority` ascending).
  - `least_busy`: Selects the account with the lowest utilization (`active / max_concurrency`).
  - `fill_first`: Prefers the active account / registration order until saturated or cooled down.
  - `weighted`: Smooth weighted round-robin based on each account's `weight` (`1..=100`).
- **Per-account settings (`accounts.json`, up to 64 accounts)**: Each saved account supports `enabled` (pool on/off without removing credentials), `priority` (lower value = higher tier), `weight` (`1..=100`), `maxConcurrency` (`1..=16`), and optional `proxyUrl` (overrides global ECPA proxy; supports `direct` to bypass proxy). Reauthorizing an isolated account preserves these settings.
- **Concurrency limits, queuing & live sessions**:
  - `max_global_concurrency` (default `16`, `1..=128`): Global simultaneous in-flight API turn cap.
  - `max_live_sessions` (default `64`, `4..=256`): Live suspended Responses / pending tool-call sessions across accounts; tool waits release HTTP concurrency slots while keeping their own CLI session alive.
  - `queue_wait_ms` (default `3000`, `0..=60000`): Async slot queue timeout when all healthy slots are momentarily busy; client disconnect immediately cancels waiting without leaking slots.
- **Per-(account, model) cooldown & safe pre-output failover**:
  - Upstream `RESOURCE_EXHAUSTED` (429), `UNAVAILABLE` (503), and `DEADLINE_EXCEEDED` (504) record exponential backoff cooldowns scoped to `(account, model)` (`cooldown_base_secs` default `60`, `cooldown_max_secs` default `600`). Upstream `UNAUTHENTICATED` (401) / `PERMISSION_DENIED` (403) mark the account `auth_required` until re-verified or reset.
  - Fresh (unpinned) requests transparently fail over up to `max_failover_attempts` (default `2`) times **strictly before** HTTP 200 / first output text / tool calls are emitted. Mid-stream failures never replay, `400 InvalidRequest` never cools down or fails over, and pinned continuations (`previous_response_id`, Chat `tool_call_id`, `history_match`) always stay sticky on their owning account.
- **Non-blocking operations & aggregated model catalog**:
  - API request admission is decoupled from interactive UI actions: adding a new account, editing settings, verifying another account, or resetting cooldowns does not block healthy accounts serving API traffic. Destructive actions (`logout` / `remove`) protect the target account if it has active requests and only abandon that account's suspended sessions.
  - When `account_pool` is enabled, `/v1/models` and the CPA `ecpa-antigravity-acp` provider register the deduplicated union of models advertised by all enabled verified pool accounts, while routing each request only to accounts supporting that model.

## Chat Completions and streaming contract

The public Chat Completions endpoint and the default Responses route continue to use CPA's existing authentication, routing, and protocol translators. CPA's Chat-to-Chat response translator passes completion JSON through, so the internal listener must produce complete Chat Completions frames itself.

Successful streams begin with an assistant role delta, followed by text or indexed function tool calls, a single terminal finish reason (`stop` or `tool_calls`), and `[DONE]`. All chunks retain the same completion ID, model, and creation time. Bounded output queues apply backpressure and remain cancellable instead of dropping chunks during a burst. Token usage is omitted when the official CLI does not provide API token counts; `stream_options.include_usage` does not cause fabricated usage.

The listener waits for the first upstream event before committing HTTP 200. Failures before output return an HTTP error through CPA's existing error handling. Failures after output emit a terminal SSE error without a success finish reason or `[DONE]`. This preserves the distinction between an upstream failure and a completed assistant turn. An official CLI quota failure or retry message remains an upstream execution issue; protocol framing cannot restore exhausted model quota.

The isolated CPA contract test checks text replies and tool call/result round trips through both public protocols, including all combinations of streaming and non-streaming tool delivery and continuation. It also checks startup and mid-stream upstream failures. The official ACP process is simulated in this test; no model quota is consumed.

## Native Responses and live continuation boundary

With the [native executor](../plugins/acp-responses/README.md) installed and enabled on the same machine, use the existing CPA client key at HTTP `POST /v1/responses`. The authenticated loopback backend implements JSON and SSE for text, supported inline images, and client function tools. Keep the bridge bearer and response IDs private: each `resp_acp_…` ID contains 192 random bits and is a single-use capability for the next turn. With `previous_response_id`, send **only** new user input, or all function outputs in the last response. The same account, model, instructions, and tool definitions are required; omitted instructions and tool definitions inherit the live session configuration. If the first request combined top-level `instructions` with system/developer input messages, a continuation may repeat just that same top-level string. The other directives stay in the original ACP session; do not replay them. An explicit null or empty string denotes no top-level instructions and cannot clear a nonempty value on a live session. To change instructions, start a new response without the previous ID. A replay, invalid tool batch, or attempted history rewrite cannot append to another turn. Normal idle IDs expire after three minutes; pending tool calls expire within ten minutes. New turns and completed tool barriers use the same live ACP process/session ID without replaying history. There is no persistent ID or cross-process resume guarantee. WebSocket, compaction, and stored Responses are out of scope.

Codex CLI 0.166.0 in HTTP mode sends `store: false` and replays its full input on `exec resume` without a parent ID. The native executor forwards a bridge-local digest of CPA's authenticated caller identity. ECPA reuses the live session only when exactly one unexpired turn under the same CPA client key has an exact semantic history prefix and matching account, model, instructions and tools. It sends only the new user input or the current tool-result batch to ACP. Different CPA keys and forged headers or body metadata cannot claim that turn. A missing scope, edited/ambiguous text history or expired live worker starts a fresh text replay; an unmatched pending function result fails closed. Clients sharing a CPA key are the same caller for this purpose; use separate keys to isolate unrelated callers. The bounded history is in memory only, not a public stored-Responses feature.

Responses function namespaces retain their original namespace/name on the wire; ECPA gives each declared function an unambiguous internal MCP name. Codex `client_metadata` is validated and ignored, not used as a session key. Linux live acceptance used real Codex CLI 0.166.0, CPA 8.0.78 and signed-in official ACP 1.5.14. With the explicit [ACP Codex profile](../plugins/acp-responses/README.md#codex-cli-opt-in-profile), it verified `exec resume` delta-only reuse and a read-only Codex MCP function result on the original ACP prompt. The same setup did not complete with the default long Codex instructions; the bridge does not silently strip or shorten them.

The MCP adapter registers a stdio server through `session/new.mcpServers` and correlates concurrent calls/results by ID. Tool output must be supplied by the API client; the ACP client does not give the agent terminal or filesystem capabilities. Linux synthetic tests exercise parallel calls over one stdio connection, out-of-order results, successive batches, and replay rejection. Real signed-in CLI behavior on native platforms still needs acceptance.

**Pinned-core limitation (CPA 8.0.78, `db7f177d`):** in both HTTP modes, `openai-compatibility` forwards to `/chat/completions` and loses `previous_response_id`; a `codex` API-key route forwards to `/responses`, but the HTTP executor deletes the field before forwarding. The latter retained `function_call_output` in a recording loopback probe, which is insufficient without the parent ID. Keep the managed OpenAI-compatible provider for Chat and model discovery. The optional native plugin routes only HTTP Responses to the original Responses backend while preserving CPA authentication. Real pinned-core tests verified unmodified continuation IDs and tool results in JSON and SSE. Without the installed and enabled plugin, public Chat and translated Responses remain the compatibility fallback and require full history for continuity.

When ACP returns a structured prompt error, ECPA preserves the reported error category without forwarding the upstream's raw message or internal detail. Explicit authentication, permission, resource limits, unavailable service, and deadline failures can be reported as HTTP 401/403/429/503/504 before output, or as a terminal Responses SSE `error` after output. The loopback event carries both the category and numeric status; CPA 8.0.78 normalizes the public event and preserves the category in `error.code`, not the numeric field. Ordinary ACP progress or assistant text is not used to infer quota or account restrictions. A silent turn still ends at the normal deadline; ECPA neither retries nor rewrites submitted instructions to recover it.

### ACP 提示词兼容配置（可选，无需更改 CPA 路由）

默认 `prompt_profile` 为 `append`：客户端的 system/developer 内容仍走 CLI 声明的系统追加字段。若客户端允许把这些内容当作**普通上下文，而不是系统级指令**，可先关闭 ACP API 接入，在全局 ACP profile 的 `bridge.json` **合并** `"prompt_profile": "first_turn_context"`（保留 `port`、`enabled`、`account_pool` 等字段），再重新开启。恢复时改回 `append`。设置对这个监听器的 Chat 与原生 Responses 请求都生效；不同信任级别的调用方不宜共享此配置。需要系统优先级的约束应保留默认模式。

新 ACP 会话仅在首个 `session/prompt` 前置一个 `Client context:` 文本块，内容按原始顺序保留；无指令不添加空块。会话续接、精确历史重放匹配和工具回传不重复注入。无状态 Chat 每次新建 ACP 会话，仍会附带该次上下文。ECPA 自己的工具权限和系统级工具使用说明不降级。配置不按错误触发，不改变账号、模型、会话匹配或配额，也不保证任一模型会接受请求。

只规范化两处 ECPA 自有排版：回放多段历史时，桥接器在角色标签前生成的一行空行省略，消息内的空行和标签不变；当整段指令**逐字节等于**随附的 [`codex-acp-instructions.md`](../plugins/acp-responses/codex-acp-instructions.md) 加上单个 UTF-8 BOM，或该模板前加精确标题 `# ECPA ACP instructions` 与两个 LF 时，只移除 BOM 或标题。混合或改写的文档原样保留，用户消息、工具结果不参与模板匹配。超过限制报错，不截短。
